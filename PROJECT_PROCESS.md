# College Track Data: Project Process and Reflection

I started this project to build a dataset of women’s outdoor college track and field performances that I could use for sports analytics. The focus is on the 400 meters, 100-meter hurdles, 400-meter hurdles, and long jump at selected schools in the SEC, ACC, Big Ten, and Big 12. The project originally focused on recent seasons, but I expanded the intended coverage to 2016–2026. As the project grew, I realized that collecting results was only part of the work. I also needed a consistent way to check, organize, and document them.

One of the biggest mistakes was treating files with results as if they represented complete seasons before fully checking their coverage. Some early datasets contained only part of a season, while my goal was to include every meet and each athlete’s performances, rather than just season-best marks. To address this, we revised the collection process to use TFRRS all-performance listings and check coverage against official schedules and available meet results. We also added audit scripts and coverage documentation. This helped identify gaps, although historical coverage checks are still ongoing, and the working files should not all be described as exhaustive.

Another challenge was missing athlete information, especially class years. I wanted the data to include context about the athlete at the time of the meet, but some records did not have that information. We reviewed roster information and corrected several missing class years in the ACC data. Any information that still needs verification should remain marked as missing. This taught me that a field being filled in does not automatically make it accurate, and that checking the source matters more than making the dataset look complete.

File organization also became harder as more schools and years were added. We addressed this by keeping raw CSV files for each school and season and separate processed files combining schools by conference and year. We rebuilt ACC and SEC datasets, removed outdated files and placeholders, and updated the README to explain the structure. Later, we split the combined data into four event files covering 2016–2026. These files make it easier to work on one event at a time and prepare tables and charts for analysis.

GitHub introduced its own problems. I used terminal commands to move CSV files into the repository, stage changes, commit them, and push updates. When a Git index lock caused problems in the original Desktop repository, we created a working copy under the Projects folder and successfully committed and pushed the event files. This experience showed me why troubleshooting file locations and repository state is part of managing a data project.

So far, this project has taught me to review coverage before calling data complete, preserve raw files, and document corrections. The next steps are to finish checking gaps, verify remaining athlete details, and create event-level tables and charts. The project is still developing, but the collection and organization process is much clearer than when I started.
